# Select dropdowns / listbox popups inside modal dialogs — 2026 state of the art

**Date:** 2026-10-14
**Method:** primary sources only (W3C/APG, specs, MDN, first-party library docs and repos, browser-engine blogs). Every claim is followed by `[source: URL]`. No application code — architecture descriptions only.

## Question

In React web apps (2025–2026 state of the art), what are the best practices for rendering SELECT dropdowns / listbox popups **inside modal dialogs**?

Context: a React SPA (Vite, React 19) with an in-house design system that has (a) a kit Modal built on a portal + overlay + focus trap, and (b) a kit Select that uses progressive enhancement: native `<select>` everywhere, upgraded to an `appearance: base-select` custom picker in browsers supporting it, gated by `@supports (appearance: base-select)` (stated as Chrome/Edge 134+, Safari 27+ — see §6 for the corrected support matrix).

---

## 1. ARIA Authoring Practices (APG)

- The APG treats the select family as three separate patterns: the **combobox pattern** (editable or select-only input + popup), the **listbox pattern** (a standalone list of options), and the **dialog (modal) pattern**. There is no dedicated "select in dialog" pattern; composition rules come from combining them. [source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/] [source: https://www.w3.org/WAI/ARIA/apg/patterns/listbox/] [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/]
- **Modal dialogs are closed worlds**: "Windows under a modal dialog are inert… users cannot interact with content outside an active dialog window", and "modal dialogs contain their tab sequence… Tab and Shift + Tab do not move focus outside the dialog… modal dialogs do not provide means for moving keyboard focus outside the dialog window without closing the dialog." Everything a select needs (popup, options) must therefore live **inside** the dialog's world. [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/]
- Dialog semantics: container has `role="dialog"`, `aria-modal="true"`, is labelled via `aria-labelledby`/`aria-label`; on open, "focus moves to an element contained in the dialog". [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/]
- **Escape ordering**: the APG combobox pattern specifies that when focus is in the popup, "Escape: Closes the popup and returns focus to the combobox", and for the combobox itself "Escape: Dismisses the popup if it is visible." The dialog pattern separately specifies "Escape: Closes the dialog." Composed, the intended stack is **innermost-first**: a first Escape closes the select popup, a second closes the dialog. [source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/] [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/]
- A subtle precision: the **standalone** APG listbox pattern does not define an Escape key at all (it is a widget you navigate with arrows/type-ahead, not a dismissible popup) — Escape semantics for a *popup* listbox come from the combobox pattern. [source: https://www.w3.org/WAI/ARIA/apg/patterns/listbox/] [source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/]
- Keyboard requirements for the popup itself: arrow keys move between options, Home/End jump to first/last, and "Type-ahead is recommended for all listboxes, especially those with more than seven options." A select-in-modal must keep all of this while the dialog is open. [source: https://www.w3.org/WAI/ARIA/apg/patterns/listbox/]
- Popup association: on a combobox, `aria-haspopup` must correspond to the popup role (`listbox`, `grid`, `tree`, or `dialog`). [source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/]

## 2. Layering / top layer

- The **Top Layer** is a browser-internal stacking mechanism you cannot address with `z-index`. MDN lists exactly which things go there: fullscreen elements, `<dialog>` opened via `showModal()`, popover elements, and — since customizable select — **"The drop-down picker of a customizable `<select>` element, once opened."** Because both the modal dialog and the select picker are top-layer citizens, they stack by **open order, not by z-index**, and the picker (opened later) sits above the dialog. [source: https://developer.mozilla.org/en-US/docs/Glossary/Top_layer]
- MDN's dialog reference confirms modal `<dialog>` is "promoted to the top layer" and pairs it with `::backdrop`. [source: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog]
- **Why fixed/absolute dropdowns get clipped**: a dropdown rendered inside a scrollable/`overflow: hidden` ancestor (typical modal body) is clipped by that ancestor, and any ancestor that creates a stacking context can bury it. Floating UI states the fix explicitly: `FloatingPortal` "Portals the floating element into a given container element — by default, outside of the app root and into the body… necessary to ensure the floating element can appear outside any potential parent containers that cause clipping (such as `overflow: hidden`), while retaining its location in the React tree." [source: https://floating-ui.com/docs/FloatingPortal]
- The **portal-to-body + no-z-index** discipline is also the official Radix guidance: in the "Select content not showing in Dialog due to z-index" issue, the maintainer answered that "Having the dialog content in a portal should ensure it's always on top. What you might be missing is a new stacking context at the root of your app… there should be no need for any specific `z-index` on any of the overlaid contents (dialog, select, popovers, etc) and they should stack naturally." [source: https://github.com/radix-ui/primitives/issues/2773]
- **floating-ui** is the positioning engine used by Headless UI and recommended standalone (the modern successor to react-popper in React codebases); its React layer supplies `useFloating`, `useInteractions`, `FloatingPortal`, `FloatingFocusManager`, `useDismiss`, plus positioning middleware (`offset`, `flip`, `shift`, `size`). [source: https://floating-ui.com/docs/react]
- **Is top layer recommended in 2026 for dropdown-in-modal?** For the *native* path yes — MDN documents that the base-select picker is a popover in the top layer and that this "ensures that the picker displays on top of other elements and interacts gracefully with other popovers on the page (for example, closing unrelated popovers that are already open)". For the *custom* path, the library consensus is portal-to-body (DOM order / Radix layer system) rather than hand-rolled `z-index`; React Aria, Radix, Base UI, and Headless UI all keep floating UI out of the modal's DOM subtree. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select] [source: https://floating-ui.com/docs/FloatingPortal]

## 3. Focus management

- **Focus traps need a stack, not a boolean.** `focus-trap` (the reference trap library) provides `trapStack` so multiple traps coordinate — "If the focus trap is not at the top of the `trapStack`, it will not be unpaused… until all traps higher on the stack have been deactivated" — plus `isolateSubtrees` (applies `inert`/`aria-hidden` to siblings), `escapeDeactivates`, `allowOutsideClick`, and `clickOutsideDeactivates` (which "takes precedence over `allowOutsideClick`"). A select popup inside a trapped modal must be understood as *inside* the trap, not as an escape from it. [source: https://github.com/focus-trap/focus-trap/blob/master/README.md]
- Known Safari caveat: "Safari does not tab through all elements on a page… users must enable Preferences > Advanced > Press Tab to highlight each item on a webpage" or traps "will not work the way you expect them to" (focus-trap issue #783). [source: https://github.com/focus-trap/focus-trap/blob/master/README.md] [source: https://github.com/focus-trap/focus-trap/issues/783]
- **Escape closes the innermost layer first** — this is implemented, not just prescribed: floating-ui's `useDismiss` defaults `bubbles.escapeKey` to `false`, documented as: "if you're dismissing a tooltip inside a dialog using the esc key, you likely don't want the dialog to dismiss as well until a second key press, which is the default behavior." Headless UI documents "Esc when listbox is open → Closes listbox". React Aria's `useOverlay` keeps a module-level stack of visible overlays where "only the top-most overlay will close at once". [source: https://floating-ui.com/docs/useDismiss] [source: https://headlessui.com/react/listbox] [source: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/overlays/useOverlay.ts]
- **Focus entry/exit**: Radix Dialog exposes `onOpenAutoFocus` / `onCloseAutoFocus` on `Content` so a host can decide whether initial focus lands in the dialog and where focus returns on close; the APG says focus opens *inside* the dialog and Radix returns focus to the trigger on Escape. React Aria's `useOverlay` similarly handles focus return when the top overlay unmounts. [source: https://www.radix-ui.com/primitives/docs/components/dialog] [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/] [source: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/overlays/useOverlay.ts]
- Practical failure mode to design against: if the popup is portaled outside the trap's DOM subtree, naive traps either let focus wander "behind" the modal or drop focus to `<body>` when the popup unmounts (see the React Aria "focus restored to body" report in §8).

## 4. Click / pointer outside behavior

The core 2026 problem: a portaled select popup is **DOM-outside** the dialog but logically **inside** it. Each library solves it with an explicit layer/dismissal stack:

- **React Aria** — `useOverlay` maintains `visibleOverlays` (a ref stack): only the top-most overlay reacts to Escape and to outside interaction, and `shouldCloseOnInteractOutside` is evaluated per-overlay, so a click on a lower overlay's content dismisses only the overlay above it. [source: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/overlays/useOverlay.ts]
- **floating-ui** — `useDismiss`'s `outsidePress` can be a predicate; its own docs use exactly this case: "The toast is not inside the Dialog's React tree, so we need to add a guard to consider it a child of the Dialog to prevent the Dialog's outside press from closing it." Composition of `escapeKey`/`outsidePress` bubbling is per-event configurable. [source: https://floating-ui.com/docs/useDismiss]
- **Radix** — outside presses are handled by `DismissableLayer`; a 2026 change (PR #3928, `deferPointerDownOutside`) deferred `pointerdown`-outside dismissal for Dialog/Popover, and open issue #4134 asks to extend the same deferral to Select/HoverCard/Tooltip/NavigationMenu — i.e., Radix is actively fixing "the parent modal closes before/while the child popup handles the press". Historically the nested case surfaced as #2121 ("clicks in the Popover are closing [the Dialog]"), where the workaround was the `modal` prop on the Popover root. [source: https://github.com/radix-ui/primitives/issues/4134] [source: https://github.com/radix-ui/primitives/issues/2121]
- **Base UI** — `Select.Root`'s `modal` prop defaults to `true`: "user interaction is limited to the select: document page scroll is locked and pointer interactions on outside elements are disabled." While the select is open, the rest of the page (including the dialog behind it) is explicitly inert-ed instead of clickable. [source: https://base-ui.com/react/components/select]
- **Headless UI** — `ListboxOptions` also has `modal` defaulting to `true`: "Whether to enable accessibility features like scroll locking, focus trapping, and making other elements `inert`." [source: https://headlessui.com/react/listbox]
- **Background/inert marking** — modal content behind is marked via `inert` (Radix Dialog: content underneath is "rendering the content underneath inert"; APG: "Windows under a modal dialog are inert"), and library portals can accidentally mark *too much*: Base UI issue #5577 reports the portal container receiving `aria-hidden` + `data-base-ui-inert`, i.e. an `aria-hidden` blanket can swallow the open popup if the popup portals into a hidden subtree. [source: https://www.radix-ui.com/primitives/docs/components/dialog] [source: https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/] [source: https://github.com/mui/base-ui/issues/5577]
- **Recommended strategies in 2026** (as practiced by all four libraries): (1) an overlay/layer stack where only the top layer dismisses; (2) pointerdown-based, deferred outside detection so the child popup gets the press first; (3) explicit "this portal belongs to the dialog" guards rather than DOM-ancestry checks; (4) `inert`/`aria-hidden` on the background — never on subtrees that contain an open popup.

## 5. Mobile

- **Native pickers are OS-level and always win**: classic `<select>` on iOS/Android opens a system picker sheet that is rendered by the OS above any web content, including modal overlays — the modal never clips it. MDN frames `base-select` precisely as the opt-out of this behavior: "the `base-select` value causes the `<select>` not to render outside the browser pane or to trigger built-in mobile operating system components." [source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/appearance]
- **iOS zoom quirk (≥16px rule)**: Google's first-party `model-viewer` repository documents it verbatim: "Mobile WebKit/Blink engines (such as Safari and Chrome on iOS) automatically zoom in the entire page viewport when a text or numeric input is focused if the computed font-size is strictly less than 16px. This page-level zoom remains locked even after the input is blurred" — and its fix explicitly styles "inputs and selects" to 16px. So the quirk covers form controls including selects. [source: https://github.com/google/model-viewer/commit/98c3817ee8de02ac11cf3de8a9464ded6c170191]
- **Viewport-hack mitigation is dead**: since iOS 10, WebKit "ignore[s] the `user-scalable`, `min-scale` and `max-scale` settings" — you can no longer disable focus zoom via the viewport meta tag, leaving font-size ≥16px as the reliable fix. [source: https://webkit.org/blog/7367/new-interaction-behaviors-in-ios-10/]
- **Touch-through bugs on mobile selects**: Radix issues #1658 / #2696 ("Selecting an option triggers a touch event on elements positioned behind") were closed — option taps used to fall through to the modal/page beneath; this is the mobile-specific sibling of the desktop outside-press problem. iOS tap pass-through on overlays remains open in #4209. [source: https://github.com/radix-ui/primitives/issues/1658] [source: https://github.com/radix-ui/primitives/issues/2696] [source: https://github.com/radix-ui/primitives/issues/4209]
- **Guidance found (and not found)**: MDN is the accessible primary source for the custom-vs-native trade-off (progressive enhancement, custom styling in supporting browsers, native picker otherwise) — see §6. Apple's Safari Web Content Guide confirms form controls are stylable ("Form controls in Safari on iOS are resolution independent and can be styled with CSS… You can create custom checkboxes, text fields, and select elements") but predates customizable select. The Apple HIG "Pickers" page is JavaScript-rendered and could not be retrieved in this session; no web.dev article dedicated to web select pickers was located. [source: https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/DesigningForms/DesigningForms.html] [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
- **Net**: on mobile, option A (keep native) is the *safest* architecture — the OS sheet is inherently above the modal. Turning on `base-select` on mobile replaces that sheet with an in-page popover (top layer), which works but inherits the same in-modal considerations as desktop (Escape/outside-press/top-layer ordering) and removes the OS picker by design.

## 6. `appearance: base-select` (CSS UI / Open UI)

- **Spec status**: `appearance: base-select` is defined in CSS Basic User Interface Level 4 (`valdef-appearance-base-select`), standard track, not experimental. [source: https://drafts.csswg.org/css-ui-4/#valdef-appearance-base-select] [source: https://github.com/mdn/browser-compat-data/blob/main/css/properties/appearance.json]
- **Open UI status**: the "Customizable Select Element (Explainer)" is listed under **Graduated Proposals** — the design is settled (opt-in via `appearance: base-select` on the `<select>` *and* on `::picker(select)`; earlier `<selectmenu>`/`<selectlist>`/markup-based proposals were dropped). Motivation per Open UI: hand-rolled controls "can lead to reduced performance, reliability, and accessibility compared to the native form control elements." [source: https://open-ui.org/components/customizable-select.explainer/]
- **Browser support as of 2026-10** (MDN BCD for `appearance`): Chrome **135** (not 134 — the brief's stated floor is off by one), Safari **27**, Firefox **149 behind flags** (`dom.select.customizable_select.enabled`, `layout.css.appearance-base.enabled`; Gecko bug 1974787). MDN's guide banner says "Limited availability — This feature is not Baseline." The `listbox` appearance sub-value is Chrome 145+, experimental. [source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/appearance] [source: https://github.com/mdn/browser-compat-data/blob/main/css/properties/appearance.json] [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
- **How the built-in picker layers**: "The picker is a popover. Therefore, when the picker is opened, its contents (contained within the `::picker(select)` pseudo-element) are promoted to the top layer. This ensures that the picker displays on top of other elements and interacts gracefully with other popovers on the page." MDN repeats it in the `appearance` reference: "The picker is rendered in the top layer, similar to a popover." So in supporting browsers the picker is **above modal dialogs by spec**, with no z-index work. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select] [source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/appearance]
- **Positioning**: the select button and picker have an implicit anchor reference (CSS Anchor Positioning), with browser-default `position-try` fallbacks when the picker would overflow the viewport — relevant inside a modal, where viewport space is reduced. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
- **Known bugs inside modal/dialog**: no first-party report was found of the base-select picker failing to stack above a `<dialog>`. The closest open layering report is Open UI #1204 (picker options overlapping a fixed navbar), which shows positioning vs. fixed UI is still being shaken out. [source: https://github.com/openui/open-ui/issues/1204]
- **Caveats**: MDN warns "Some JavaScript frameworks block these features; in others, they cause hydration failures when Server-Side Rendering (SSR) is enabled" — an argument for keeping the `@supports` gate (your current design) rather than unconditioned styling. Chromium's status API endpoint was unavailable during this research; support numbers come from MDN BCD instead. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]

## Options summary

### Option A — Native select as-is inside the modal (no changes; includes the current `@supports` base-select upgrade)

- **Pros:** zero code; the classic OS picker renders above the modal by definition (§5); in supporting browsers the base-select picker is spec'd into the top layer above the dialog (§6); Escape/keyboard/type-ahead are browser-provided; no bundle cost; already the architecture of the kit Select. [source: https://developer.mozilla.org/en-US/docs/Glossary/Top_layer] [source: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/appearance]
- **Pros:** progressive enhancement with a working fallback is exactly MDN's prescribed pattern for customizable select. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
- **Cons:** unenhanced desktop browsers get the classic look, not the design-system styling; iOS focus-zoom quirk applies if form font-size <16px; no control over popup styling/positioning on mobile once base-select disables the OS picker.

### Option B — Custom listbox portaled to body, positioned with floating-ui (DIY)

- **Pros:** full control over markup, styling, and positioning; portal solves clipping; `useDismiss` gives configurable Escape/outside-press bubbling. [source: https://floating-ui.com/docs/FloatingPortal] [source: https://floating-ui.com/docs/useDismiss]
- **Cons:** you now own APG conformance (focus management, `aria-activedescendant`/roving tabindex, type-ahead) — the entire category of bugs in §8 becomes yours; heaviest engineering cost of all options. [source: https://www.w3.org/WAI/ARIA/apg/patterns/combobox/]

### Option C — Top-layer-first architecture (native `<dialog>` / Popover API for both modal and picker)

- **Pros:** spec-native stacking (dialog and picker both top-layer, ordered by open sequence), native light-dismiss and `::backdrop`; matches where the platform is heading (base-select picker *is* a popover). [source: https://developer.mozilla.org/en-US/docs/Glossary/Top_layer] [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
- **Cons:** still requires careful Escape/focus composition (APG innermost-first) — top layer fixes stacking, not event ownership; Firefox flag-gated base-select means the custom-picker half is not yet universal. [source: https://github.com/mdn/browser-compat-data/blob/main/css/properties/appearance.json]

### Option D — Adopt a library (Radix / React Aria / Base UI / Headless UI) for dialog + select

- **Pros:** battle-tested layer stack: `modal` coordination, deferred pointer-outside, managed focus restore — the §8 bug list is theirs, already triaged; declared APG conformance. [source: https://base-ui.com/react/components/select] [source: https://headlessui.com/react/listbox] [source: https://github.com/adobe/react-spectrum/blob/main/packages/react-aria/src/overlays/useOverlay.ts]
- **Cons:** replaces or duplicates the existing kit Modal/Select (migration cost of an in-house design system); largest bundle delta (`react-aria-components` 272.6 KiB gzip; even `@headlessui/react` 61.5 KiB gzip); library-specific gotchas still exist (Base UI #5577, Radix #4134). [source: https://bundlephobia.com/] [source: https://github.com/mui/base-ui/issues/5577]

### Option E — Disable the base-select enhancement inside modals (classic native only, scoped by CSS/context)

- **Pros:** one predictable rendering path inside dialogs; sidesteps any not-yet-filed base-select-in-modal issue; no top-layer interplay between picker and dialog to reason about.
- **Cons:** loses design-system styling exactly in the most branded surface (dialogs); forks behavior between modal/non-modal contexts — two visual states to test; while other page selects keep the modern picker (§6), producing inconsistent UX.

## Recommendation

**Adopt Option A (native as-is, keeping the `@supports (appearance: base-select)` upgrade) as the default, with these guardrails; hold D as the fallback and treat E as a temporary kill-switch, not an architecture.**

Rationale:

1. **The layering problem is already solved by the platform.** MDN's top-layer contract puts the classic OS picker, the base-select picker, and the modal `<dialog>` into one ordered mechanism — a dropdown opened from inside a modal renders above it without any z-index work (§2, §6). This is precisely the class of problem that generated Radix #2773 and most of §8.
2. **Event ownership is browser-managed on the native path.** Escape ordering, outside-press, and scroll behavior for the native picker are the engine's job; for base-select the picker is a popover with popover dismissal semantics. The library machinery in §4 (overlay stacks, deferred pointerdown) exists precisely because *custom* popups must reimplement this. [source: https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Customizable_select]
3. **It matches the team's existing investment.** The kit Select's progressive enhancement is MDN's recommended pattern verbatim; the only corrections needed are factual (Chrome floor is **135**, Firefox is flag-gated in 149) and defensive (keep font-size ≥16px on form controls in modals for iOS). [source: https://github.com/mdn/browser-compat-data/blob/main/css/properties/appearance.json] [source: https://github.com/google/model-viewer/commit/98c3817ee8de02ac11cf3de8a9464ded6c170191]
4. **Escalation path is evidence-driven**: if a custom (non-native) popup is ever added inside the modal, port it to body and copy the *patterns* D proved — top-layer stack, `modal`-style coordination, deferred pointer-outside, innermost-first Escape — before pulling in a whole library (B is the expensive fallback; D only when APG conformance debt outweighs bundle/migration cost).
5. **E stays available** as a scoped kill-switch (e.g., if a browser regression in base-select-in-modal appears) but should not be the default: forking picker behavior between modal and non-modal contexts trades a hypothetical risk for a guaranteed UX inconsistency.
